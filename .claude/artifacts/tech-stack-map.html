Syncattend 기술 스택 맵

학생 앱(Flutter) · 교수 웹(React) · 백엔드(FastAPI)가 무엇으로 통신하고 데이터가 어디로 흐르는지 한 장으로 정리한 설계도.

전체 설계도

굵은 인디고 화살표는 공기 중을 이동하는 물리 채널(소리·빛), 회색 화살표는 네트워크·DB 연결.

공기 중 물리 채널 (강의실 안에 있어야 받을 수 있음) 네트워크 · DB 연결

연결 총정리

누가 누구에게, 무엇으로 보내는지 화살표 단위로 나열한 표.

연결기술하는 일
교수 웹 → 학생 앱초음파 17–18.5kHz (Web Audio → 마이크)공간 증명 — 그 강의실 안에 있는지
교수 웹 → 학생 앱동적 QR · 15초 회전시간 증명 — 지금 이 순간의 세션
교수 웹 → 백엔드REST JSON (vite /api 프록시)과목·시간표·세션 열기·출결 집계
학생 앱 → 백엔드REST + JWT Bearer출석 인증 제출 (QR + 초음파 + 기기 UUID)
백엔드 → 학생 앱SSE (Server-Sent Events)인증 결과 · 결석 경고 실시간 푸시
백엔드 ↔ RedisTTL 키 (15초)QR·오디오 nonce 단발성 보관, 이메일 인증 코드
백엔드 ↔ PostgreSQLSQLAlchemy (async) + Alembic출결·과목·기기·수강 영속 저장

출석 인증 한 번의 흐름

세션 열기부터 결석 경고까지, 60초 인증 창 안에서 일어나는 일.

  1. 세션 열기 — 교수 웹에서 세션 생성. FastAPI가 sessions (week_number 1–15) 행을 만들고 Redis에 QR·오디오 nonce 발급 (15초 TTL).
  2. 신호 방송 — 교수 화면에 동적 QR 표시 + 스피커로 초음파 송출 (Web Audio API · 17–18.5kHz).
  3. 수신 — 앱이 QR 스캔 (mobile_scanner) + 마이크 녹음 (record · 48kHz) → FFT로 초음파 nonce 복호.
  4. 제출 — POST /attendance/verify (JWT 헤더 + qr_token + audio_nonce + device_uuid).
  5. 검증 — 서버가 Redis로 nonce 교차 검증, 60초 창 확인, PostgreSQL UNIQUE 제약으로 계정·기기별 딱 1회 강제.
  6. 결과 — present 응답 + 과목별 결석 경고 전송 (SSE · 2회 주의 / 3회 위험).
전부가 함께 물리는 구조 — JWT는 누구인지, 기기 UUID는 어느 기기인지, 동적 QR은 언제인지, 초음파는 어디에 있는지를 각각 증명한다. 한 축이 뚫려도 나머지가 막는 다층 방어.
