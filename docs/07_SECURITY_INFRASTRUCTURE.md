## 1. 인증·인가 보안

- **JWT** 기반 인증(로그인/갱신). 역할(학생/교수)별 권한 분리 — 교수는 담당 수업만 관리.
- **단기 토큰(nonce)**: QR 토큰·음향 토큰 모두 Redis 15초 TTL. 만료·재사용 방지로 캡처·녹음 재생 공격 창을 최소화.
- **일회용 nonce(원격 릴레이 차단)**: 서버는 각 nonce를 일회용(single-use)으로 처리하여 이미 사용·검증된 토큰의 재제출을 거부한다. 원본 소지자가 먼저 인증하면 토큰이 즉시 소모되어 릴레이 수신자는 재사용 불가.
- **교차 검증**: QR(시간/신원) + 음향(공간/근접성)을 서버에서 동시 검증. 단일 신호 단독 신뢰 금지.

> **핵심 기술 리스크(선검증)**: 노트북 스피커 18~20kHz 방출 + 학생 기기 마이크의 강의실 거리·소음 복호는 확정 사실이 아닌 **프로젝트 최대 기술 리스크**. M1~M2 feasibility spike로 선검증하고, 부족 시 가청 하단 대역·화면 보조 신호로 대체(보안 계층 설계에는 영향 없음).

## 2. 신원 위조(다계정 대리) 방어

QR·음향은 "기기가 강의실에 있다"는 **근접성**만 증명하고 "조작자가 계정 주인인가"라는 **신원**은 증명하지 못한다. 이 신원 문제를 다음 계층으로 방어한다.

- **1분 인증 창**: 인증은 교수가 여는 약 60초 동안만 가능. "내 출석 → 로그아웃 → 친구 계정 → 재인증" 수법을 **현실적으로 어렵고 불안정하게** 만든다(완전 불가능 단정은 아니며 근본 차단은 서버 유일성). 교수가 창 연장 가능.
- **서버측 유일성 규칙(실질 핵심 방어)**: 서버가 "한 세션당 계정 1회·동일 기기(UUID) 1회 출석"을 강제. 프론트로 우회 가능한 공격을 서버에서 차단.
- **앱 생성 UUID 기기 바인딩**: 학생 앱(Flutter)이 최초 실행 시 랜덤 UUID를 생성해 iOS 키체인/Android 키스토어(`flutter_secure_storage`·`flutter_udid`)에 저장하고 계정에 바인딩. 서버는 바인딩된 UUID와 일치하는 기기에서만 출석 인정.
- **기기 변경 재등록 + 자동 바인딩 금지**: UUID 소실·기기 교체 시 학교 이메일(@wku.ac.kr) 재인증을 통과해야 새 기기 재바인딩. **새/미지의 UUID의 최초 바인딩은 자동으로 하지 않고 반드시 이메일 재인증을 강제**한다. 변경 이력 로깅.
- **프론트엔드는 UX 넛지만(비보안)**: 하드 로그아웃 쿨타임·세션 잠금은 서버 규칙과 중복이며 정상 사용자 오탐(배터리 교체·앱 재시작·실수 로그아웃)이 커 두지 않는다. 프론트는 보안 경계가 아님.
- **생체인증(선택 확장)**: Face ID/지문으로만 쓰이는 하드웨어 키로 서버 챌린지 서명(WebAuthn/FIDO 원리). 1분 창 도입으로 필수 아님, 향후 옵션.

### 기기 식별 방식 — 왜 앱 생성 UUID인가 (정직한 근거)

- 순수 하드웨어 고유 ID(IMEI·시리얼)는 최신 iOS/Android가 개인정보 보호를 위해 앱 접근을 **차단**한다.
- `device_info_plus`가 제공하는 OS 대체 식별자(iOS `identifierForVendor`, Android `androidId`/SSAID)는 읽을 수는 있으나 **OS가 관리하는 값이라 앱 재설치·전체 삭제·팩토리 리셋 시 변할 수 있어** 바인딩 기준으로 부적합(정상 사용자 오인 차단 위험).
- 반면 앱이 생성해 키체인/키스토어에 저장한 UUID는 **앱이 통제**하며 iOS 키체인 특성상 **재설치를 넘어 유지**되어 더 안정적.
- OS 식별자를 보조 지문으로 병행하는 방안은 검토했으나, 그것이 잡는 공격(보안저장소 UUID 추출)은 탈옥·루팅이 필요한 고난도인 반면 더 쉬운 공격(여러 폰 지참)은 못 막고 오탐·복잡도만 늘어 **미채택**(보안 목적 `device_info_plus` 미사용).
- **알려진 경계(정직한 한계)**: 앱 데이터를 의도적으로 삭제하면 같은 물리 기기라도 새 UUID가 생성되어 서버에는 "새 기기"로 보일 수 있다. 이를 막기 위해 새 UUID의 최초 바인딩에 **이메일 재인증을 강제(자동 바인딩 금지)** 하여 UUID 재생성만으로는 유일성 규칙을 즉시 우회할 수 없게 한다. 재인증 후의 반복 스와핑까지 완전히 막지는 못하므로 교수 이상 탐지 대상으로 둔다.

## 3. 부정행위 대응 및 잔여 리스크

- 음향 토큰은 강의실 벽을 크게 넘지 못해 물리적 근접성 근거가 되고, 15초 갱신 + 60초 창으로 원격/다계정 대리를 고비용화.
- **잔여 리스크 명시**: 같은 강의실 공범 중계, 음향 재생 스푸핑, **친구 폰 여러 대 지참**은 완전 차단 불가. 목표는 "0% 차단"이 아니라 구조적 난이도·비용·발각 위험 상승 + 교수 인 더 루프 최종 확인. 여러 폰 지참은 물리적으로 눈에 띄므로 교수 이상 탐지·무작위 확인으로 대응.
- 신호 실패/창 놓침은 자동 결석이 아님 → 미인증 표시 후 교수 정정·창 연장.

## 4. 개인정보 (Privacy-by-Design)

- **동의**: 최초 사용 시 수집 항목(출결, 근접성 신호, 기기 정보)·목적 고지 및 동의.
- **데이터 최소화**: 위치·음향 원자료 미저장, "근접성 검증 통과 여부(boolean)"만 기록, 음향 토큰은 세션 후 폐기.
- **기기 정보 최소화**: 앱 생성 UUID(무작위 값)만 바인딩에 사용, 하드웨어/OS 식별자 수집·저장 안 함. 기기 변경 이력은 이상 탐지 목적 로그로만 보관.
- **보관 기한**: 출결 데이터는 학사/법정 규정 기한까지만 보관 후 파기.
- **민감정보 회피**: 진단서 등 건강정보는 시스템이 자동 판독하지 않고 교수 수동 검토·승인 경로로 분리(AI 판독은 v-next 제외).
