# Syncattend (SDAS) — 대규모 운영 시나리오

가장 부하가 크거나 위험이 큰 상황들을 골라, 무슨 일이 일어나고 시스템이 어떻게
대응하는지 **간단명료하게** 정리한다. 각 시나리오는 [상황 → 흐름 → 시스템 대응
→ 핵심 근거]로 구성한다.

관련 문서: 설계는 `03_ARCHITECTURE_DESIGN.md`, 요구사항은 `02_PRD.md`,
스키마는 `07_DATABASE_SCHEMA.md`, 리스크는 `12_RISK_MANAGEMENT.md`.

---

## S1. 수업 시작 피크 — 300명이 동시에 인증

**상황**: 대형 강의(300명)가 시작하고, 교수가 인증 창을 열자마자 수백 명이
동시에 `POST /attendance/verify`를 쏜다.

**흐름**
```
교수: 세션 시작 → 1분 인증 창 open, Redis에 15s QR/음향 nonce 발급
학생 300명: QR 스캔 + 음향 복호 → verify 동시 요청 (피크)
```

**시스템 대응**
- QR/음향 nonce 검증·소모는 **Redis 원자 연산**(`SET NX`)으로 처리 → PostgreSQL 행 락 경합 회피.
- 개별 출석은 가벼운 append. 유일성은 `UNIQUE(session_id, student_id)` + `UNIQUE(session_id, device_uuid)`가 DB에서 보장.
- 누적 결석 등 조회성 데이터는 Redis 선캐싱으로 SELECT 스탬피드 완화.

**핵심 근거**: 쓰기 경합을 Redis로 흡수하고 DB는 유일성만 담당 (PRD FR-3, TRD TR-4).

## S2. 동시 마감 러시 — 여러 강의실이 정각에 함께 종료

**상황**: 12:00 정각, 수십 개 강의가 동시에 인증 창을 닫으며 미인증자를
결석 처리한다.

**흐름**
```
각 세션 종료 → 미인증자(전체가 아닌 변경분 Delta)만 결석으로 확정
```

**시스템 대응**
- **Delta Batch UPDATE**: 전원이 아니라 미인증자(delta)만 묶어 한 번에 UPDATE → 락 점유·I/O 최소화.
- 이미 present인 학생은 건드리지 않음 (교수는 결석자만 opt-out 처리).

**핵심 근거**: 마감 부하를 "변경분만" 처리해 대량 UPDATE 폭발을 방지 (PRD FR-3(B), TRD TR-4(B)).

## S3. 대리 출석 공격 — 한 폰으로 여러 계정

**상황**: 학생이 본인 인증 후 로그아웃하고 친구 계정으로 로그인해 같은 폰으로
재인증을 시도한다.

**흐름 → 결과**
```
① 내 계정 인증 성공  →  present
② 로그아웃 → 친구 계정 로그인 → 같은 기기로 verify
   → UNIQUE(session_id, device_uuid) 위반 → 거부 (duplicate)
```

**시스템 대응**
- 세션당 **기기 UUID 1회**만 출석 가능 → 같은 폰의 두 번째 계정 차단.
- 1분 인증 창이라 "여러 계정 순차 인증"의 시간 여유도 좁음.
- 앱 데이터를 지워 UUID를 새로 만들어도, 새 UUID는 **자동 바인딩 금지** → 이메일 재인증 필요.

**핵심 근거**: 서버 유일성 규칙이 프론트 우회를 무력화 (PRD FR-2.2, 리스크 R3).

## S4. 원격 릴레이 공격 — 강의실 밖 친구에게 QR/음향 전달

**상황**: 강의실 안 공범이 QR 화면·음향을 캡처해 강의실 밖 학생에게 실시간 전달.

**흐름 → 결과**
```
공범이 nonce 캡처 → 밖의 학생에게 전송 → 밖의 학생 verify 시도
   → 그 nonce가 이미 소모됐거나 15초 만료 → 거부 (nonce_reused / expired)
```

**시스템 대응**
- 모든 nonce는 **1회용(consume-on-verify)** + **15초 TTL**. 먼저 쓴 사람이 소모하면 재사용 불가.
- 음향은 벽을 잘 넘지 못해 물리적 근접성도 요구.

**핵심 근거**: 일회용 nonce가 릴레이 성공 비용을 크게 높임 (PRD FR-1.1, 리스크 R1·R2).

## S5. 기기 교체 러시 — 신학기 대량 재등록

**상황**: 신학기, 폰 교체·앱 재설치로 수백 명이 동시에 기기 재등록을 요청한다.

**흐름**
```
새 UUID로 로그인 → /devices/register가 409 (자동 바인딩 안 함)
→ /devices/reregister/request (학교 이메일 @wku.ac.kr)
→ 이메일로 받은 코드 입력 → /devices/reregister/confirm
→ 기존 바인딩 비활성화 + 새 UUID 활성화 + DeviceChange 로그 기록
```

**시스템 대응**
- 인증 코드는 **Redis에 짧은 TTL·1회용**으로 저장 → 대량이어도 영속 저장 부담 없음.
- 도메인(`@wku.ac.kr`) + 로그인 계정 일치 **이중 확인**으로 오남용 차단.
- 모든 교체는 `device_changes`에 감사 기록 → 잦은 스와핑은 이상 탐지 대상.

**핵심 근거**: 자동 바인딩 금지 + 이메일 소유 증명으로 UUID 재생성 우회를 차단 (PRD FR-2.4, 리스크 R4·R9).
> 참고: 현재 이메일 발송은 **개발 스텁**(코드가 로그로 출력)이며, 운영 전 SMTP/SES 연동 필요.

## S6. 주 여러 번 수업 — 요일별 시간 분리 시간표

**상황**: A과목은 주 2회(월 1교시 + 화 1교시), B과목은 수요일 3시간 연속(1~3교시).
이런 서로 다른 시간표를 한 시스템에서 관리한다.

**흐름**
```
교수: 과목 개설 → 주간 슬롯 등록
   A과목: POST /courses/A/schedules {월,1,1} + {화,1,1}   (2줄)
   B과목: POST /courses/B/schedules {수,1,3}               (1줄)
수업일: 세션 생성 시 schedule_id로 "이번 회차가 어느 슬롯인지" 지정
   POST /sessions {course:A, week:3, schedule:월슬롯}  → 3주차 월 회차
   POST /sessions {course:A, week:3, schedule:화슬롯}  → 3주차 화 회차
```

**시스템 대응**
- `course_schedules`에 **슬롯 1개 = 1줄** → 주 N회를 자연스럽게 표현(정규화 1NF).
- 3시간 연속은 `start_period=1, end_period=3` **한 줄**로 표현.
- `sessions.schedule_id`로 같은 3주차라도 월 회차 / 화 회차를 **명확히 구분**.
- `UNIQUE(course_id, day_of_week, start_period)`로 슬롯 중복 방지.

**핵심 근거**: 시간표를 정규화 테이블로 분리해 "주 여러 회 + 요일별 시간"을 정확히 관리 (DB `07`).

## S7. 주차 누적 결석 경고 — 15주차에 걸친 축적

**상황**: 한 학기 동안 과목별로 1~15주차 출결이 쌓이고, 특정 과목에서 결석이
누적된 학생에게 경고를 보낸다.

**흐름**
```
주차마다 session(week_number) 생성 → 출석/결석 기록 축적
학생이 출석 인증하는 순간 → 그 과목의 결석 횟수 집계
   결석 2회 이상 → 주의(warning)
   결석 3회 이상 → 위험(danger)  → SSE / 응답으로 즉시 경고
```

**시스템 대응**
- 결석 집계는 **과목 경계로 분리**(`absence_count(student_id, course_id)`) → 과목이 섞이지 않음.
- 주차는 `sessions.week_number`(1~15)로 관리 → "N주차 결석"을 명확히 구분.
- 임계값은 설정값(`risk_warning_threshold=2`, `risk_absence_threshold=3`)으로 조정 가능.

**핵심 근거**: 주차·과목 단위 축적으로 정확한 위험군 판별 (PRD FR-4, TRD TR-5, DB `07`).

---

## S8. 근접성 신호 실패 대량 발생 — 소음·저가 마이크

**상황**: 소음이 큰 대형 강의실에서 다수 학생의 음향 복호가 실패한다.

**흐름 → 결과**
```
음향 복호 실패 → verify 미완료 → 자동 결석 아님, "미인증(pending)" 표시
교수: 인증 창 연장/재개 또는 대시보드에서 즉석 정정
```

**시스템 대응**
- 신호 실패는 **결석이 아니라 pending** → 정당한 학생이 피해 보지 않음.
- 교수 인 더 루프(창 연장·수동 정정)가 최종 안전망.

**핵심 근거**: 폴백을 기본값으로 두어 오탐 방지 (PRD FR-5, 리스크 R6·R7).
